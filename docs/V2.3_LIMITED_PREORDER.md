# V2.3 Limited Preorder

## 目标与边界

V2.3 验证一条最短真实闭环：V2.1 需求信号达标，V2.2 协作项目和设计授权有效，平台开放限量预售，消费者提交可核验的订单意向或人工确认付款，达标后进入生产，未达标或取消则关闭未付款订单并处理真实退款义务。

本阶段不包含物流系统、优惠券、会员、多商户结算、复杂税务、自动分账或完整购物车。物流字段仅用于已有履约记录，不能冒充已接入物流服务。

## 角色与准入

- 发起人：只有管理员能配置、开放、暂停、结算、取消、进入生产和归档活动。
- 设计师：作品作者必须通过独立的 `ProjectDesignAuthorization` 明确接受授权；管理员和项目主理人不能代签。
- 消费者：必须登录、选择启用的 SKU、填写 1 至 20 件的整数数量，并接受活动当时锁定的完整条款正文。
- V2.1 活动：只能从 `ACTIVE` 或 `COMPLETED` 的需求活动进入 V2.3；`DRAFT`、`PAUSED`、`CANCELLED` 不得复用。
- 项目：公开可见、作品通过公开质量门槛、状态为 `PREORDER_READY`，且项目冗余授权状态与真实授权记录都为 `ACCEPTED`。
- 需求：以 V2.1 人工确认意向件数达到 V2.1 目标为准；不得使用 `currentCount` 作为 V2.3 成团件数。
- 商品：至少一个 `APPROVED` 商品，正整数分价、目标量、独立硬限量、截止日后的预计发货日、完整说明及至少一个启用 SKU。
- SKU：尺码、颜色、正整数容量必填；覆盖价只能留空或为正整数分价。启用 SKU 容量合计必须等于商品硬限量。
- 活动：成团目标、总限量、UTC 截止时间、条款版本和至少 40 字的条款正文必填；目标不得大于可售容量。

## 数据模型

V2.3 只新增字段和关系，不改写 V2.1 的 `PresaleCampaign.status/currentCount/targetCount`：

- `PresaleCampaign`：独立的 `preorderStatus`、成团口径、目标、总限量、截止时间、条款正文、人工付款指引、内部决策原因、消费者可见状态说明及生命周期时间戳。
- `ProjectProduct`：`preorderLimit` 是硬容量；`targetQuantity` 仍是商品目标，二者不得混用。`preorderCampaignId` 锁定活动归属。
- `ProjectOrder`：关联 `preorderCampaignId`，保存商品、SKU、价格、容量、截止时间、预计发货、条款正文和付款指引快照。
- `CommerceStateEvent` 和 `AdminLog`：同一事务记录活动/订单状态、操作者、原因和结算指标。
- `CommerceRefund`：只有 `SUCCEEDED` 的真实退款记录及足额金额，才能把付款或订单标为已退款。

## 活动状态机

| 当前状态 | 允许进入 | 核心条件 |
|---|---|---|
| `NOT_STARTED` | `OPEN`, `CANCELLED` | 完整准入检查；开放时锁定商品、SKU、容量和条款 |
| `OPEN` | `PAUSED`, `GOAL_REACHED`, `FAILED`, `CANCELLED` | 达标可提前结算；未到期且未达标不能伪装失败 |
| `PAUSED` | `OPEN`, `GOAL_REACHED`, `FAILED`, `CANCELLED` | 恢复时重新执行准入检查 |
| `GOAL_REACHED` | `PRODUCTION`, `CANCELLED` | 进入生产前再次核对合格件数 |
| `FAILED` | `CLOSED` | 所有退款义务已由真实退款记录结清 |
| `PRODUCTION` | `CANCELLED`, `CLOSED` | 生产异常取消前，未付款生产订单逐笔标为取消并记录履约异常，已付款订单逐笔进入退款流程；正常结束要求所有订单进入终态，完成订单必须有送达记录 |
| `CANCELLED` | `CLOSED` | 所有退款义务已结清 |
| `CLOSED` | 无 | 历史记录只读；普通项目资料可重新规划 |

同态重放为无操作；每次真实迁移用旧状态 CAS，防止双击和并发写入产生重复事件。

## 订单、容量与成团

- 订单状态、付款状态、履约状态是三条独立但有组合约束的状态轴。
- 容量按真实 `ProjectOrder.quantity` 汇总，不按订单笔数或金额。
- 商品、SKU、活动三层容量在 `Serializable` 事务中核对并创建订单，避免超售。
- 未过期的预留、所有已付款/部分退款资金义务、已确认及生产后的订单持续占用容量；只有安全终态才释放。
- `CONFIRMED_ORDER` 仅统计 `CONFIRMED` 且未退款的真实人工确认订单意向。
- `PAID_ORDER` 的数据模型与规则只为下一批试点预留；本批服务端硬性禁止配置、开放、恢复和新建付款订单，直到产品内具备可核验的真实退款记录闭环。
- 同一用户、活动、商品、SKU 的有效订单不能被新请求静默覆盖；修改或异常由平台人工处理。

## 失败、取消、付款与退款

- 未付款订单在失败或取消时进入 `CANCELLED`，记录原因和时间。
- 已付款或部分退款订单只能进入 `REFUND_PENDING`，不能伪造 `REFUNDED`。
- 生产、发货、完成等不可逆组合会阻断批量结算，要求人工异常处理。
- 活动失败、取消、结束或未开始时，不得新增待确认付款或已付款义务。
- 本批所有 V2.3 订单都禁止新增 `PENDING` 或 `PAID` 付款义务，仅验证真实订单意向；人工付款状态能力不代表平台已接入自动支付，也不能绕过此限制。
- 功能开关关闭只停止新订单；历史订单、退款和履约义务仍可查看和处理。

## 页面与审计验收

- 消费者：开放活动可见成团口径、目标、总限量、截止时间、商品说明、材质护理、SKU 价格/容量、预计发货、完整条款和付款指引；非开放状态仍可查看活动结果；订单页保留所有快照。
- 设计师/项目方：授权请求、接受、拒绝、撤销与活动状态原子联动；开放期撤销会暂停接单，达标或生产后不能绕过管理员异常流程。
- 管理员：预售工作台完成配置、准入、开放、暂停、恢复、结算、取消、生产、归档；订单管理按真实退款证据和履约组合校验。
- 数据隔离：V2.2 合作意向只查询 `preorderCampaignId = null`；V2.3 订单只查询非空活动关联，避免公开计数和页面重复。
- 审计：所有生命周期动作必须分别填写至少 4 字的内部审计原因和消费者可见状态说明；公开页面只读取后者，状态和关键数据在同一事务写入事件及管理员日志。

## 开发批次

1. 交易安全基础：幂等下单、不可变快照、容量事务、订单/付款/履约基础规则。
2. 准入与完整生命周期：独立活动状态、三层容量、结算/退款边界、三端页面、并发 CAS、法律透明度和回归隔离。
3. 生产试点与运维演练：在真实环境执行迁移备份、功能开关、小流量订单/退款演练、监控告警、磁盘与共享上传目录治理；不扩展非核心电商功能。

每个批次必须统一完成 Prisma 校验、TypeScript、全量脚本回归、构建、独立提交、PR、合并和部署验证后，才能进入下一批。
